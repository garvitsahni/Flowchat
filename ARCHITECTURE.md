## 2. Components

### 2.1 Data Pipeline (offline, run before/during Day 1-2)
- **Input**: ARGO NetCDF files (Indian Ocean subset, INCOIS or Ifremer FTP)
- **Tooling**: Python, `xarray`, `netCDF4`, `pandas`
- **Steps**:
  1. Download float profile files for target region/date range
  2. Parse into flat records: float_id, cycle_number, lat, lon, timestamp, depth/pressure, temp, salinity, QC flags
  3. **Filter/flag by QC**: drop or mark readings with QC flags indicating bad/uncertain data (ARGO QC flag 4 = bad, flag 3 = probably bad — exclude both from default queries, but retain in DB with flag visible for the explainability panel)
  4. Load into PostgreSQL with PostGIS geography columns for lat/lon
- **Output**: populated `argo_measurements` table + precomputed `qc_stats` per float/region/month for fast uncertainty checks

### 2.2 Backend (FastAPI)
- `POST /query` — main endpoint. Accepts `{question: str, language: "en"|"hi"}`. Returns structured response (see §4).
- `GET /health` — liveness check for demo stability
- Responsibilities:
  - Route question to AI Orchestrator
  - Enforce guardrails before executing any generated SQL
  - Run uncertainty check against `qc_stats`
  - Assemble final response payload (answer text + chart data + explainability metadata)

### 2.3 AI Orchestrator
- **NL → SQL**: Gemini API, few-shot prompted with schema + ~15-20 example Q→SQL pairs (see `SCHEMA_AND_PROMPTS.md`)
- **NL → Answer text**: second Gemini call (or same call, structured output) to phrase the final answer in natural language, in the requested language (English/Hindi)
- **Comparative queries**: orchestrator detects comparison intent (keywords + few-shot examples) and issues two SQL queries (target period + baseline average) rather than one
- Output format: strict JSON (see Structured Outputs pattern) — never free text SQL, to keep parsing deterministic

### 2.4 Guardrail Layer
- SQL generated by the LLM is **never executed directly**. Before execution:
  - Reject any statement that isn't a `SELECT`
  - Reject queries referencing tables/columns outside the known schema
  - Execute against a **read-only DB role** (defense in depth)
  - Row/time limit caps to prevent runaway queries
- On rejection: return a graceful "I couldn't safely answer that" response — never surface a raw DB error to the user

### 2.5 Uncertainty Engine
- After SQL executes, check `qc_stats` for the queried region/time window:
  - Float count below threshold (e.g., <3 floats) → attach `confidence: "low"` + explanation string
  - No data at all → graceful "no data available for this query" response, with suggestion of nearest available region/time
- For comparative queries: also checks baseline period has sufficient float density before claiming an anomaly

### 2.6 Frontend (React + Vite)
- **Chat panel**: message history, input box, language toggle (EN/HI)
- **Response renderer**: dynamically renders the right visualization based on response `type` field:
  - `depth_profile` → line chart (Plotly)
  - `trajectory` → map with float path (Leaflet/Mapbox)
  - `time_series` → line chart, time on x-axis
  - `comparison` → grouped/dual chart
- **Explainability panel**: collapsible drawer showing SQL used, float IDs, QC-excluded count, confidence level
- **Design system**: see `DESIGN.md` — build components via 21st.dev/Magic MCP against these tokens

## 3. Data Flow (single query, happy path)

1. User types question in chat → frontend POSTs to `/query`
2. Backend calls AI Orchestrator → returns `{sql, intent_type, language}`
3. Guardrail layer validates SQL → executes against read-only Postgres connection
4. Uncertainty engine checks float density for the queried scope → attaches confidence metadata
5. AI Orchestrator (2nd pass) turns raw result rows into a natural-language answer in the requested language
6. Backend assembles final JSON: `{answer_text, chart_type, chart_data, confidence, explainability: {sql, floats_used, qc_excluded_count}}`
7. Frontend renders answer bubble + chart + explainability drawer

## 4. Response Contract (Backend → Frontend)

```json
{
  "answer_text": "In March 2023, the Arabian Sea was 1.4°C warmer than the 5-year average.",
  "language": "en",
  "chart_type": "comparison",
  "chart_data": { "...": "..." },
  "confidence": "high | low",
  "confidence_note": "Based on 14 floats reporting in this period.",
  "refusal_reason": "",
  "explainability": {
    "sql": "SELECT ...",
    "floats_used": ["2902123", "2902456"],
    "qc_excluded_count": 37,
    "time_range_queried": "2023-03-01 to 2023-03-31"
  }
}
```

`refusal_reason` is **additive** (optional, default `""`): when `chart_type` is `"none"`
the backend sets it to one of `out_of_scope` (question can't be answered from this schema),
`no_data` (region/dates outside the ingested Indian-Ocean subset), or `unsafe` (guardrail
blocked the intent). The frontend must render the corresponding empty state instead of a
blank panel — no code path should silently return an unattributed number.

This contract is the single most important artifact for parallel dev — lock it Day 1 so
frontend can build against mock JSON while backend/AI catch up.

## 5. Tech Stack Summary

| Layer | Choice | Why |
|---|---|---|
| Frontend | React + Vite | Team's default, fast iteration |
| Charts | Plotly | Handles depth-profile + time-series well, minimal config |
| Map | Leaflet | Lighter than Mapbox, no API key friction during demo |
| Backend | FastAPI | Async, fast to scaffold, good with Pydantic response contracts |
| DB | PostgreSQL + PostGIS | Geo-queries on float lat/lon are first-class |
| AI | Gemini API | Team's existing experience, strong structured-output support |
| Data processing | Python (`xarray`, `pandas`) | Standard for NetCDF/scientific data |
| Component gen | 21st.dev / Magic MCP | Rapid premium UI scaffolding against design tokens |

## 6. Deployment (for demo stability)

- Avoid demoing off localhost if possible — deploy backend + DB to a small cloud instance
  (Railway/Render for backend, managed Postgres) and frontend to Vercel/Netlify
- Keep a local fallback ready in case of live network issues at venue
- Seed DB with the final ingested dataset well before demo — don't run ingestion live
